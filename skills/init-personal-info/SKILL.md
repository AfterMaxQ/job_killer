# 个人信息初始化

## Purpose

把用户提供的求职信息整理成**事实优先、证据友好、可人工维护**的 Markdown 档案，供其它求职 Skill 读取。

用户不需要理解 Evidence Unit、Evidence Strength 等内部术语。Agent 负责通过自然对话收集信息，再整理成稳定 Markdown。

## Core Rules

- 只记录用户明确提供或明确确认的事实，不猜测、不补齐不存在的信息。
- Markdown 是候选人档案的 Source of Truth；不要把 JSON、数据库或机器专用 Schema 作为主存储。
- 原始事实与“这能证明什么”分开保存；Evidence 不能反过来修改事实。
- 没有真实数字时允许定性记录，不为了“量化”制造数据。
- 用户更新某一字段或经历时，只修改相关内容，不无故覆盖其它档案。
- 求职方向属于运行时数据，只写入档案，不修改其它 Skill 文件。

## 目录结构

使用：

```text
个人信息/
├── 基本信息.md
├── 教育背景.md
├── 技能能力.md
├── 求职方向/
│   └── 目标方向.md
├── 工作经历/
│   └── <经历名称>.md
├── 项目经历/
│   └── <项目名称>.md
├── 比赛经历/
│   └── <比赛名称>.md
└── 证据索引.md
```

目录可以为空，但已经收集到的信息必须写入对应 Markdown。一个项目或一段工作经历优先单独一个文件，避免所有内容堆在一个超长文件里。

## Workflow

### 1. 检查现有档案

先检查 `个人信息/`。

- 不存在：创建目录和必要 Markdown。
- 已存在：先读取已有内容，判断用户是补充、修正还是新增。
- 用户只更新一个模块：只处理该模块。
- 不得因为目录结构与示例不同就删除用户已有资料；在需要时保留内容并整理到当前结构。

### 2. 收集基本信息

按当前求职需要收集：

- 姓名
- 联系电话
- 邮箱
- 当前所在地
- 当前身份
- 可选公开链接，如 GitHub / 作品集 / LinkedIn
- 用户主动提供的其它必要字段

保存为：

```markdown
# 基本信息

- 姓名：
- 电话：
- 邮箱：
- 所在地：
- 当前身份：
- 公开链接：
```

没有的字段直接省略，不保留空占位。

### 3. 收集教育背景

对每段学历记录：

- 学校
- 专业
- 学历
- 起止时间
- 辅修/双学位（如有）
- GPA / 排名（仅真实且用户愿意展示时）
- 相关课程、奖项、科研（如有）

保存为 `个人信息/教育背景.md`。

### 4. 收集技能与能力

不要只问“会哪些技术”。根据用户领域自然询问：

- 实际使用过哪些工具、技术、方法或业务方法论；
- 在什么场景使用；
- 能独立做到什么；
- 哪些只是学习、接触或课程使用；
- 有哪些证书、语言或专业资格。

保存为 `个人信息/技能能力.md`。

推荐内容是事实清单，不需要提前写成最终简历文案：

```markdown
# 技能与能力

## 数据分析

- Python：在两个课程/个人项目中用于数据清洗和分析
- SQL：用于基础查询和指标统计

## 语言

- 英语：...
```

### 5. 收集求职方向

保存为 `个人信息/求职方向/目标方向.md`：

```markdown
# 求职方向

## 目标岗位

- ...

## 偏好行业

- ...

## 当前阶段

...

## 求职重点

...

## 其他偏好

...
```

只记录用户真实偏好。用户更换方向时更新该文件，不修改 Skill 本身。

### 6. 收集工作 / 项目 / 比赛经历

每次只讨论一段经历。对用户保持自然提问，至少弄清以下信息：

1. 这是什么经历，发生在什么时间？
2. 你具体负责什么？
3. 为什么要做这件事，解决的实际问题是什么？
4. 哪些部分真正由你本人完成？
5. 过程中做了什么关键判断、方案选择或取舍？
6. 最终有什么真实结果、交付或规模？没有数字也可以。
7. 有哪些边界容易被误解或夸大？例如“参与部署”不等于“负责生产部署”。

根据领域再补充必要问题，但不要为了填模板强行追问无关项。

推荐经历文件结构：

```markdown
# 经历名称

## 基本信息

- 时间：
- 角色：
- 类型：

## 背景

...

## 实际工作

- ...

## 实际成果

- ...

## 使用技术 / 方法

- ...

# 能力证据

## E1｜能力名称

### 事实

...

### 可以证明

- ...

### 证据强度

3 / 5

### 适合支持

- ...

### 表达边界

- ...
```

Evidence 详细语义由 `build-resume/references/evidence-model.md` 定义。初始化档案时不要求每段经历都必须有完整 Evidence；事实完整性优先。

### 7. 建立 / 更新证据索引

`个人信息/证据索引.md` 用于快速导航：

```markdown
# 能力证据索引

## 数据分析

- 工作经历/示例经历.md / E1

## 自动化

- 项目经历/示例项目.md / E2
```

索引不能成为唯一事实来源。若索引与具体经历冲突，以经历文件为准，并修正索引。

### 8. 用户确认

完成当前收集范围后：

1. 展示新增/修改了哪些 Markdown 文件；
2. 摘要列出关键事实；
3. 对仍不确定的信息明确标记“未确认”，不要自行填补；
4. 让用户可以直接手改 Markdown，后续 Skill 必须尊重这些修改。

## Evidence Strength

整理 Evidence 时可使用 0–5 级：

| 等级 | 含义 |
|---:|---|
| 0 | 没有证据 |
| 1 | 了解 / 接触 |
| 2 | 课程 / 学习 / 简单实验 |
| 3 | 项目中实际使用 |
| 4 | 独立或核心完成 |
| 5 | 真实业务 / 生产环境 / 有明确结果 |

只有事实足够时才写等级。JD 是否需要该能力不能改变等级。

## Failure Handling

- 用户记不清数字：记录可确认的定性结果，不估数字。
- 用户只知道“参与”：保留“参与”的事实，不自动升级成“独立负责”。
- 用户没有某类经历：不创建虚假占位经历。
- 某项 Evidence 的边界不清楚：先保留原始事实，把更强能力 Claim 留给后续确认。

## Validation

完成前确认：

- [ ] 所有主数据都是 Markdown；
- [ ] 没有把用户未提供的信息当事实；
- [ ] 经历中的实际工作与实际成果区分清楚；
- [ ] Evidence 能回到明确事实；
- [ ] Evidence Strength 没有因目标 JD 被人为提高；
- [ ] `目标方向.md` 只保存求职画像，没有要求修改其它 Skill；
- [ ] 用户可以不依赖任何程序直接读懂和编辑档案。
