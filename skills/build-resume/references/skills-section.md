# Skills / Core Capabilities Section

技能区的目标不是展示候选人认识多少名词，而是让招聘者快速理解：**候选人具备哪些与当前岗位相关的能力，这些关键词如何组合成实际能力，并且这些能力能否被经历证明。**

## 默认语义

优先采用：

```text
能力主题：关键技术 / 方法；证据信号
```

示例（完全虚构）：

```text
后端工程：Java、Spring Boot、MySQL、Redis；能够独立完成 REST API、数据层与缓存链路开发

数据分析：Python、SQL、Excel、可视化；完成过从数据清洗、指标拆解到业务汇报的完整分析任务
```

不要把这两个能力主题当成固定分类。实际能力簇必须由当前 JD + Candidate Evidence 动态生成。

## 生成流程

1. 读取 `job-model.md` 的核心能力；
2. 读取 `match-matrix.md` 中证据强度和策略；
3. 读取 `positioning.md` 的 Top Signals；
4. 选择 2–5 个最有招聘价值的能力簇；
5. 每个能力簇只保留能够形成信号的关键词；
6. 如果有足够事实，用一句短证据信号说明“能做到什么”；
7. 检查每一行能否在工作、项目、教育或证书中找到来源。

## Strategy A：Capability-first（默认）

适合：

- 实习生；
- 应届生；
- 技术或专业能力结构清晰；
- 招聘者需要快速理解候选人的能力地图。

结构：

```text
能力主题：代表性工具 / 方法；证据信号
```

示例：

```text
AI 应用工程：Python、FastAPI、RAG、Agent Workflow；完成模型调用、工具编排与服务接口的完整项目实践
```

要求：

- 能力主题优先于工具名；
- 关键词数量以信息密度为准，不规定固定数量；
- 证据信号必须来自真实经历；
- 不需要每行都写“熟练掌握”。

## Strategy B：Keyword-dense

适合：

- JD 明确列出大量工具、平台或资格；
- ATS 匹配明显重要；
- 工具本身就是岗位筛选条件，例如特定 CAD、ERP、云平台、编程框架、财务系统。

仍需按能力或工作场景分组，例如：

```text
数据处理：SQL、Python、Excel Power Query
BI 与汇报：Power BI、Tableau、PPT
```

不要退化为：

```text
技能：SQL、Python、Excel、Power BI、Tableau、PPT、Git、Docker、...
```

Keyword-dense 也必须满足：

- 关键词真实使用过；
- 证据强度足够；
- 不把 JD 中用户不会的词复制进来；
- 同义、重叠工具不无限堆叠。

## Strategy C：Minimal

适合：

- 已有较强工作经验；
- 工作成果本身能够证明大部分能力；
- 页面空间紧张；
- 技能区不是主要卖点。

只保留 2–3 个能力簇，甚至只写最核心工具：

```text
核心能力：B2B 商业分析、市场规模测算、竞争格局研究
数据工具：SQL、Excel、Power BI
```

不要为了保持模板完整而硬凑 4–5 类。

## 动态能力簇

能力簇来自当前岗位，而不是固定职业表。

可能出现：

- LLM Serving
- 系统与性能工程
- 云平台工程
- 数据分析
- 财务建模
- 商业研究
- 用户研究
- 项目交付
- 供应链分析
- 自动化测试
- 视觉设计
- 客户解决方案
- 运营增长

这些只是示例，不是白名单。

### 能力簇命名原则

优先使用招聘者能直接理解的工作能力：

```text
好：数据分析、市场研究、系统工程、项目交付
弱：工具类、其它、综合技能、软件
```

## 证据信号

证据信号是对真实能力范围的短总结，不是自我评价。

好：

```text
完成从调研、数据整理到管理层汇报的分析任务
```

弱：

```text
具备优秀的数据分析能力
```

好：

```text
独立完成服务开发、部署与日志排查
```

弱：

```text
熟练掌握全栈开发
```

如果没有足够 Evidence 支持一句证据信号，可以只写经过筛选的关键词，不要制造能力描述。

## 技能强度与措辞

Evidence Strength 约束表达强度：

- 1–2：通常不放核心位置；如岗位需要，可按“了解 / 学习 / 课程实践”真实表达；
- 3：可以写“在项目中使用”“完成项目实践”；
- 4：可以写“独立完成”“核心负责”，前提是事实明确；
- 5：可以强调真实业务、生产环境和结果，仍不得补不存在的数字。

不要把分值机械翻译成固定文案；只使用事实支持的语言。

## API / 工具调用边界

普通 API 调用、安装工具、照教程运行命令，不自动构成“专业技能”。

只有当候选人能够证明：

- 在真实任务中使用；
- 理解如何把工具组合进解决方案；
- 能处理边界、错误或工程问题；

才考虑作为技能信号。

例如“调用过某大模型 API”通常不足以单独成为能力簇；如果候选人设计了工具调用流程、上下文管理、错误恢复等完整 Agent 工程，则可以归入更高层的能力主题。

## ATS 与 Evidence 的冲突处理

当 JD 有重要关键词但 Evidence 较弱：

- 可以在真实范围内出现；
- 不得为了 ATS 把它升级成核心能力；
- 不得加“熟练”“精通”“生产级”等没有证据的词；
- 如果 Evidence = 0，不写。

## 禁止模式

### 纯名词仓库

```text
AI：Python、PyTorch、TensorFlow、LangGraph、RAG、vLLM、Ollama、Docker、Linux、Git
```

问题：没有能力层级，也无法判断哪些真正使用过。

### 固定分类套所有岗位

```text
语言 / 框架 / 数据库 / 中间件 / DevOps
```

只有当前岗位确实适合时才可以使用，不能成为默认 ontology。

### 把履历里没有的 JD 词塞进技能区

任何关键词必须能回到候选人档案或用户明确确认。

### 技能区承担全部证明责任

技能区只是快速信号，核心能力仍应由工作 / 项目 /教育 / 证书中的证据证明。

## Validation

- [ ] 选择了 Capability-first / Keyword-dense / Minimal 中最合适的策略；
- [ ] 能力簇来自当前 JD + Evidence，而不是固定职业模板；
- [ ] 控制在 2–5 个真正有价值的能力簇；
- [ ] 每个关键词都有事实来源；
- [ ] 证据信号没有超过 Evidence Strength；
- [ ] 普通 API 调用没有被包装成高级技能；
- [ ] 没有为了 ATS 提高熟练度；
- [ ] 工作经验很强时允许使用 Minimal，不为凑版式增加技能行。
