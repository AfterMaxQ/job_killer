# Resume Writing Standards

本文件只定义最终简历的内容表达规则。岗位理解、Evidence、匹配与 Positioning 分别由其它 reference 负责。

## 目标

让招聘者在快速扫读时理解：

- 候选人做过什么；
- 做出了什么关键判断或专业动作；
- 产生了什么真实结果；
- 这些经历为什么与当前岗位相关。

写作质量的优先级：

```text
真实性
>
证据强度
>
岗位相关性
>
信息密度
>
语言漂亮
```

## 1. Bullet 默认结构

STAR 可用于 Agent 内部理解经历，但不要求最终每一条 Bullet 都写完整 Situation / Task / Action / Result。

最终 Bullet 优先采用：

```text
Action
+
Technical / Professional Decision
+
Scope / Result
```

例如：

```text
设计自动化资料处理流程，拆分采集、清洗和结构化输出节点，使失败步骤可以单独重试并定位。
```

它已经包含行动、方案和结果，不需要额外补一段背景才能“凑 STAR”。

## 2. 动词与贡献边界

优先使用能够准确描述责任范围的动词：

- 设计
- 开发
- 实现
- 分析
- 搭建
- 优化
- 重构
- 排查
- 维护
- 推进
- 建立
- 验证
- 输出

如果事实只是“参与”，不要为了让句子更有力改成“主导”“独立负责”。

如果用户明确是独立开发或核心负责人，可以如实表达。

## 3. 技术 / 方法必须和问题绑定

避免：

```text
使用 Redis、RabbitMQ、Docker 完成项目。
```

更好：

```text
使用消息队列拆分任务提交与执行流程，并增加失败重试，使长任务无需占用同步请求。
```

技术名词的价值在于说明方案，不是展示词汇量。

## 4. 量化原则

不要求每个项目都有数字。

成果表达优先级：

```text
1. 真实业务指标
2. benchmark / 测试指标
3. 用户、数据、请求、文件等规模
4. 完成工作规模
5. 明确交付状态
6. 定性技术 / 业务成果
```

### 有真实数字

直接使用，并保持原单位、原口径。

### 没有数字但有范围

可以写：

```text
完成从数据导入、检索到接口交付的完整链路。
```

### 没有任何量化信息

如实写技术难点、方案选择和交付状态。

### 禁止

- 根据感觉补“提升 30%”；
- 根据代码行数、接口数量等未确认信息自行统计后当业务成果；
- 把教程、课程默认规模写成真实用户规模；
- 为满足“成果量化”规则虚构数字。

## 5. 项目经历

一个项目优先回答四个问题：

1. 项目解决什么真实问题；
2. 候选人本人承担什么；
3. 最有价值的 2–4 个专业动作是什么；
4. 最终交付或结果是什么。

推荐结构：

```markdown
### 项目名称｜角色

技术 / 方法：只列本项目真正用于关键工作的内容

一句话项目定位。

- Action + Decision + Scope/Result
- Action + Decision + Scope/Result

结果：真实指标、交付状态或定性成果
```

项目简介不要求统一写“谁有痛点 → 竞品差在哪 → 我的方案”，只有事实支持时才说明现有流程/方案的真实问题。

不得为了让项目显得高级而添加用户没有实现过的 Redis、Docker、缓存、分布式锁、模型、云平台等技术。

## 6. 工作 / 实习经历

工作经历优先表达：

- 真实职责范围；
- 个人具体贡献；
- 关键决策与问题解决；
- 交付结果；
- 与团队 / 业务的关系。

不要把整个团队成果全部写成个人成果。

如果候选人主要做分析、运营、产品、设计等非技术工作，使用该领域自然的专业动作，不强行套“开发 / 优化 / 技术栈”语言。

## 7. 教育背景

必须准确保留：

- 学校正式名称；
- 专业正式名称；
- 学历；
- 起止时间。

其它内容只在真实且有助于当前岗位时使用：

- GPA / 排名；
- 核心课程；
- 奖学金；
- 论文 / 科研；
- 辅修 / 双学位；
- 学术项目。

不得因为学校背景普通而改写学校名称，也不得把在线课程伪装成正式学历课程。

## 8. 技能 / 核心能力

当简历包含技能或核心能力区时，必须读取：

```text
references/skills-section.md
```

技能区不是候选人所有工具的完整库存，而是当前 JD 下最重要的能力信号。

## 9. 自我评价

默认不是必选模块。

只有当它能提供简历其它部分难以表达但又有证据支持的信息时才保留，例如：

- 工作语言；
- 特殊职业资格；
- 明确跨领域优势；
- 与岗位高度相关且有事实支持的执行特点。

避免：

```text
学习能力强、责任心强、沟通能力好、抗压能力强
```

这类没有证据、几乎适用于所有人的空泛标签。

## 10. ATS 与自然阅读

ATS 关键词应自然出现在：

- 能力主题；
- 技术 / 方法；
- 项目和工作 Bullet；
- 教育 / 资格（如适用）。

不要为了 ATS：

- 在技能区堆满 JD 原词；
- 重复同一技术多次；
- 把候选人只接触过的技术写成核心能力；
- 复制整段 JD。

## 11. 动态岗位表达

本 Skill 不使用固定职业 ontology。

“后端、前端、算法、测试”“市场、运营、财务”等可以作为具体岗位中的能力示例，但不能成为所有简历必须套用的分类。

Agent 应根据：

```text
当前 JD
+
Candidate Evidence
+
Positioning
```

动态决定模块名称和表达重点。

## 12. 信息密度

每一行都应回答至少一个问题：

- 我做了什么？
- 我怎么做？
- 为什么这样做？
- 结果是什么？
- 这证明什么？

如果一句话只起连接、装饰或重复作用，优先删除。

## 13. 篇幅

A4 单页可以作为学生 / 实习简历的默认目标，但不是比真实性和内容完整性更高的规则。

压缩优先级：

1. 删除与当前 JD 弱相关内容；
2. 合并重复能力；
3. 压缩次要项目；
4. 删除空泛自评；
5. 缩短技能区；
6. 最后再考虑排版间距。

不要为了单页删除岗位最核心的真实证据，也不要为了“填满一页”增加无价值文字。

## 14. Claim Strength

最终措辞不能超过 Evidence Strength。

示例：

```text
事实：课程项目中使用过 Kubernetes
```

可以写：

```text
在课程项目中使用 Kubernetes 完成基础部署
```

不可以写：

```text
具备 Kubernetes 生产集群运维经验
```

## 15. 终稿检查

写完 `resume.md` 后，进入 Claim Audit，不直接交付。

检查：

- [ ] 核心内容是否强化 Positioning；
- [ ] 最强 Evidence 是否获得足够篇幅；
- [ ] Bullet 是否包含真实 Action / Decision / Result；
- [ ] 没有机械套完整 STAR；
- [ ] 所有数字有事实来源；
- [ ] 技能区没有退化成名词仓库；
- [ ] 没有把弱 Evidence 写成强 Claim；
- [ ] 没有将团队成果全部归为个人；
- [ ] 没有固定职业分类残留影响陌生岗位。
